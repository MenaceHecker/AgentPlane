## Test review

The new validation agenda targets requirements: multi-replica admission, underestimation, repeated recovery, late completions, idempotency and checkpoint metadata substitution. These are planned cases, not implemented tests. The report appropriately withdraws the earlier unconditional coverage claims, but its assumption-failure fallback claim remains too strong.

Constructed counterexample, checked with a simple arithmetic model (not an implementation test or performance measurement): cap 100, `R = 25`, true consumption 100 per request. Run four requests sequentially, each ending with unknown consumption and a terminal charge of 25. Every admission satisfies the cap and `maxInFlight = 1`; final recorded `used = 100`, true consumption is 400, and excess is 300, greater than one request's usage. This case is allowed by the table's explicit assumption-failure condition. The mock's validated bound may avoid it, but that does not justify a guarantee for unvalidated/non-compliant backends.

## Security review

The checkpoint repair is consistent: `alg` and `key_id` are inside `payload`, the signature covers the entire canonical payload with a domain prefix, and the out-of-band registry controls key/algorithm/tenant authorization. Reading `key_id` to select a trusted candidate does not itself authenticate it. Negative fixtures now include metadata changes, registry mismatch, unknown keys, wrong tenant and malformed envelopes. No runtime signing or key management has been pulled into Phase 0.

Settlement now uses CAS, epochs, terminal states and excess-only late corrections; this addresses duplicate settlement and downward corrections under stated hard-bound assumptions. It does not establish actual-consumption safety when those assumptions fail and consumption is unknowable. Counter-store atomicity and data durability remain prerequisites, not implementation details to hand-wave away.

The admission record detects a store already unavailable before forwarding. The proposal correctly says that after admission an outage cannot retract already-delivered stream bytes. INSERT-only access and separate checkpoint trust are preserved. Completeness of rejected-request logging during an outage remains an explicitly documented gap. That exception and the multiple-event interpretation should be part of the owner decision, not silently treated as full FR-AUD-1 coverage.

Recommendation for that decision: use one logical request audit trail with an admission event, a completion/recovery event, and append-only correction events when necessary. Preserve `request_id`/reservation linkage, distinguish request totals from physical event counts, and make incomplete requests detectable. A writability probe alone has a race; buffering the entire response removes incremental streaming. This is a review recommendation, not owner acceptance or an authorization to change the requirements.
