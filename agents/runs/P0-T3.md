A synthetic secret in another file is still detected (negative control run in a scratch directory). This is an allowlist; it is as narrow as I could make it, and the plan asked for no *broad* allowlists. It modifies P0-T1 files and the owner/Codex should confirm they accept it.

### Finding 1: removed secrets on lines starting with "+"

### Finding 2: totals for conflicting repeated event keys
What I got wrong: `totalsFor` used a structure check that skipped all duplicate-key checks, so a chain with two events under one key but different content (`chain-conflicting-event.json`) produced totals (`req_0001:400 req_0002:9192 req_0004:0`) although the full verifier rejects it as `conflicting_event`. Deduplication silently picked one of two disagreeing events. My earlier claim that invalid chains cannot be summed was therefore incomplete. The temporary probe before the fix (deleted afterwards):
```
PROBE chain-conflicting-event.json     totalsFor ok=true reason="" totals=map[req_0001:400 req_0002:9192 req_0004:0] | verifyChain={OK:false Reason:conflicting_event ...}
PROBE chain-duplicate-correction.json  totalsFor ok=true reason="" totals=map[req_0001:400 req_0002:9192 req_0004:0] | verifyChain={OK:false Reason:duplicate_event ...}
```
Fix: the structure check now always rejects a repeat whose content differs from the first use of that key (`conflicting_event`); an identical repeat (a retried append) is tolerated for totals, because totals count each distinct key once, and the full verifier still reports it as `duplicate_event`. The identical-duplicate demonstration is kept: the duplicate-correction chain yields the distinct total 9192 while the naive sum differs.
Regression tests (committed, `internal/contractcheck/audit_test.go`): `TestAuditTotalsRefuseConflictingEventsButTolerateIdenticalDuplicates` pins both behaviours; `chain-conflicting-event.json` was added to the manifest `totals_refused` list (so `TestAuditTotalsAreRefusedForInvalidChains` refuses it); and `663c57d` makes that list's required entries explicit (conflicting event, null identity, event key from another request, unsafe integer) after my own mutation run showed removing the conflicting chain from the list went unnoticed (only a minimum count was checked).
