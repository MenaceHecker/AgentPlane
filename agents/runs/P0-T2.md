### Finding 1: concurrent reservations did not prove the overshoot bound
What I got wrong: I called the estimated reservation an "upper bound" and said estimation affected only false rejections. The reviewer's counterexample (four requests reserve 25 against cap 100, each really consumes 100) is correct: admission checks the reserved total, not final usage, and an input underestimate affects every admitted request. ADR-005's "can never exceed the cap" repeated the same unconditional claim.
Fix: (a) two reservation modes with explicit assumptions: `bounded` (input bound = UTF-8 bytes plus a per-message overhead, valid only if each token covers at least one byte, assumption A1) and `context_window` (reserve the model's maximum total tokens, no estimate, assumption A3), plus A2 (backend honors `max_tokens`, enforced by cutting streams); (b) a per-agent `inflight` counter and `maxInFlight` limit checked in the same atomic admission, with `429 concurrency_limited`; (c) the corrected invariant: I1 limits reserved totals only, and `used <= cap + sum(E_i)` with `E_i = max(0, A_i - R_i)`; (d) a guarantee table: zero overshoot when A1/A2 (or A3/A2) hold; at most one request's excess when assumptions fail and `maxInFlight = 1`; **not guaranteed** when assumptions fail and `maxInFlight > 1`; (e) any counter store must give a linearizable conditional update across agent scope, tenant scope and `inflight`, across all replicas; (f) the reviewer's arithmetic added as an adversarial validation case with expected outcomes per configuration; (g) NFR-3 row changed to "conditional, not claimed as met until the adversarial tests pass".

### Finding 2: crash and cancellation settlement could refund consumed budget

Fix (ADR-004): (a) unknown consumption is charged a validated hard per-request maximum `H` (assumption A3), not `R`; (b) `inflight` now counts requests whose provider execution may still be running, with explicit rules: increment atomically with admission, durable `forwarded_at` set before the first byte is sent, decrement exactly once via `inflight_released`, deferred to `forwarded_at + T_exec_max` (validated hard execution-time bound, assumption A4) for unknown outcomes or earlier on a late acknowledgement, with crash recovery using the durable `forwarded_at`; (c) a model without validated `H` and `T_exec_max` cannot be enabled for budgeted traffic (fail closed); (d) the guarantee table was rewritten: zero overshoot for known-consumption requests when A1/A2 hold, at most one request's maximum consumption with `maxInFlight = 1` when A1/A2 fail (because at most one request may be executing and every other request's consumption is already in `used`), not guaranteed for `maxInFlight > 1`, and no guarantee for unvalidated models; (e) I2 and the late-completion rule were requalified (provided A3/A4 are validated; excess-only correction now means `A` above the charge already made, i.e. a hard-bound violation, which also quarantines the model); (f) the sequential unknown-usage case, in-flight accounting, `T_exec_max` boundary and hard-bound violation cases were added to the validation agenda, and I state that the withdrawn "charge `R`" rule would fail the sequential case. Costs stated: a cancelled request is charged `H` and blocks the agent for up to `T_exec_max`.
Why the sequential case now holds (argument, not a test): the first unknown outcome adds `H >= 100` to `used`, so `used >= cap` and no further request is admitted in the window; `concurrency_limited` also blocks the agent until execution uncertainty ends. This is design reasoning; no implementation or measurement exists.
Corrected review: NFR-3 remains **conditional** (validated `H` and `T_exec_max`, `maxInFlight = 1`) and is not claimed as met. Whether `H` and `T_exec_max` can be validated for a given backend is an open Phase 2 / P0-T4 question.
